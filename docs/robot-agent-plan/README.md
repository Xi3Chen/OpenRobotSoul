# OpenRobotSoul 项目方案

本目录定义可部署到不同机器人型号上的具身交互运行框架的首版目标、架构边界、模块契约、事务与数据回环、实施阶段和验收方法。每个运行时实例服务一台机器人及其连接的感知/执行设备；不同机器人型号是跨部署的兼容目标，不表示多机协同。方案以云端大语言模型为语义决策能力，不要求在机器人本地运行大语言模型。

## 核心决策

系统由三个业务模块组成：

1. 机器人适配器：隐藏具体硬件差异，提供感知输入和动作能力。
2. Agent：基于云端模型理解任务、选择工具并给出下一步高层决策。
3. 事务处理流回环：维护任务和交互状态，路由事件与动作，融合反馈、判定主动任务资格并评估结果。

事件、状态、任务和动作的共享数据契约，以及认证、日志、追踪和配置属于横向运行治理职责，由三个模块共同遵守，不作为第四个业务模块。

## 当前边界

- 项目目标是支持多个经过验证的常见机器人型号；每个运行时实例只绑定一台物理机器人。
- MVP 先完成一个目标机器人的端到端接入，再在隔离测试中用第二个兼容 profile 验证配置切换，不要求同时部署或协调多台机器人。
- 感知适配器可先接入一种输入；没有相机时仍可通过语音或文本任务工作。
- 动作必须通过有参数约束的工具调用，不能将自由文本直接解释为运动命令。
- 高层推理使用云端 API；本地运行确定性的运动控制、安全监督及设备驱动。
- PicoClaw 先作为 Pi coding agent 的替代方案，在隔离工作区评估；机器人运行时 Agent 选型仍独立进行。
- VLA 模型不是 MVP 的前置条件。未来可作为某个技能或策略实现接入。
- 通过手势、语音等感知信号触发人机交互；视觉注意力可作为可选唤醒条件。
- 记忆可用于个性化和生成改进建议；生效策略须经过验证、授权和可回滚部署。
- 主动问候/探索由本地资格策略约束，云端 Agent 不得自行解除电量、环境和安全条件。
- 地图、熟人信息、电量/充电和 savepower 纳入主动探索状态与策略；熟人登记和身份使用遵循授权及隐私策略。
- 独立启动监督器负责启动健康检查、版本回退和恢复模式；云端 LLM 仅协助诊断/生成修复提案，不是安全恢复的前置依赖。
- 低风险且已预授权的插件可通过沙箱验证、权限检查和 canary 后自动部署；其他插件和代码变更需批准。

配置化的范围是选择已实现的驱动/适配器、连接参数、传感器映射、坐标和能力约束。新协议、新动作语义或未支持的控制生命周期仍需编写并验证适配器代码。

## 决策状态

这是首版实施规划，不是现有实现的代码审计。机器人型号、传感器型号、云端模型供应方、机器人运行时 Agent、运行时语言和部署拓扑仍需在技术预研后通过 ADR（架构决策记录）确定。PicoClaw 用于替代 Pi coding agent 的决定是阶段性选型，集成与隔离验收见 [Agent 选型与 PicoClaw 集成决策](11-agent-tooling-decision.md)。OpenRobotSoul 为当前项目名。

机器人代码、profile 和该机器人专属第三方依赖按 `adapters/<robot_code>/` 组织；部署目标通过 `config/robot.json` 选择已登记的静态模块。新增模块的目录、registry、profile 和验收规范见[机器人模块组织规范](12-robot-module-standard.md)。
