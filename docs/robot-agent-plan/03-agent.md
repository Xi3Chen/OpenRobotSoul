# Agent 与工具调用

## 职责边界

常驻对话进程 `openrobotsoul-dialogue` 承担自然语言规划。它链接 `third_party/picoclaw` 的 AgentLoop，负责语义理解、多轮对话（含 session 历史与摘要压缩）、任务拆解和技能选择。Dashboard 文本框提交的任务、本地唤醒后的最终转写，以及 Dashboard 通话里的最终转写，都是自然语言输入，进入同一条运行时入口，由这个进程对照当前机器人已注册技能做选择。它不启动 `cmd/picoclaw` CLI，也不执行技能。隔离工作区里的编码仍由 Go 版 PicoClaw CLI 单独承担。唤醒、未完成的中间识别和音频帧本身不是任务。关键词规则不是这些入口的规划器。

自然语言会话和编码任务共用 `config/llm.json` 中的模型配置，工具权限按任务分开。自然语言会话只能看到当前 profile 暴露的机器人技能，调用仍经事务流和本地安全检查。编码任务只在独立工作区读写文件，不能调用机器人动作，也不读取用户记忆和运行时主目录；它可以读取生产环境的模型与服务凭证（`config/llm.json`、ASR/TTS 密钥等），不再为编码任务单独申请低额度密钥。凭证仍不写入日志和任务产物。

DemoAgent 不再匹配自由文本，只用于没有模型配置时的接口测试和模拟器冒烟。本地直接调用只有 `/技能名` 或 `/技能名 参数=值` 这一种形式。它不承接 Dashboard 文本任务、实机任务或语音转写。

Agent 不直接操作硬件协议，不维护机器人权威状态，不自行认定动作已经完成，也不承担实时避障、平衡或急停。事务处理流回环负责将工具调用转为可执行命令，并等待真实反馈。

## 端云模型路径

MVP 只配置一个明确的模型调用路径，避免同一轮任务经多个互相不知情的 LLM 循环反复规划：

1. 所选运行时 Agent 直接通过选定 provider 调用云端模型；或
2. 所选运行时 Agent 调用一个受控云端 AI Gateway，由 Gateway 代理模型请求。

Dashboard 设置页把这一条路径记在本机 `config/llm.json`：provider、base_url、model、timeout 和 API key。LLM 的 API key 只保存在该文件中，不回显到接口或日志；ASR/TTS 的密钥走环境变量（见 [16](16-voice-interaction.md)），设备连接凭证由机器人模块的受控部署配置承载。统一原则：凭证由各自的加载入口读取，不进 profile，不进日志和任务产物。对话进程与编码进程都从这一份配置取模型参数（对话侧生成临时 PicoClaw Config，不读 `~/.picoclaw/config.json`）。文本任务和语音转写共用它，不为通话或本地语音再开一条规划循环；不同用户、入口与对话使用宿主生成的不透明会话键，互不串历史（见 [18](18-picoclaw-dialogue-context.md)）。

图像、唤醒、语音识别和语音合成可作为独立感知或播报服务，但必须输出有版本的结构化观测或最终文本。对话进程的任务模型调用和这些专用模型调用需在追踪里区分。最终转写交给 `openrobotsoul-dialogue` 之后，才进入技能选择。

本地不部署 LLM。断网时运行时可以完成本地安全动作、取消或等待；若无云端能力，应明确告诉用户任务暂不可继续，不用本地小模型静默替代。

## 工具设计

工具分两类，目标形态都按 agent loop 最顺手的方式暴露。机器人动作统一做成 skill：由各设备适配器或 profile 声明，除参数 schema 外还带执行情景（前置条件、完成证据、可中断性、风险等级），因为同一个动作在不同设备上的执行情景并不相同；skill 仍经 TaskRunner 与 Runtime 的参数、能力、风险、确认和本地安全检查。通用 agent 工具（读取授权记忆、查询任务状态、取消任务、提出 proposal）不触碰硬件，走 agent loop 的原生工具调用。当前对话进程是 tools=0 加单一 JSON 决策的过渡实现，切换说明见 [11](11-agent-tooling-decision.md)。工具表达高层技能而不是电机控制，命名稳定、参数类型明确、范围可验证，例（前四项是机器人 skill，后两项是 agent 通用工具）：

- head.look(yaw_deg, pitch_deg)
- base.move_distance(distance_m, max_speed_mps)
- speech.say(text)
- navigation.go_to(named_location)
- task.get_status(task_id)
- task.cancel(task_id)

工具集合按机器人能力动态提供；未声明的技能不提供给模型。交给模型的每一项包含技能名、`description` 动作介绍、参数 schema、风险等级和限制。动作介绍来自适配器能力清单；有厂商 SDK 时采用 SDK 方法声明和官方示例注释。参数范围和用户确认要求由能力清单与安全策略生成，不应只依赖提示词约束。

工具返回应表示已受理或拒绝，并携带 task_id/command_id 以及查询进度的方法。工具响应不是最终自然语言答复的证据；Agent 要根据回环汇总的执行反馈和评估结果回复用户。

## 动作复核

`confirm` 级动作在 Agent 提出之后，还要经过一层无工具复核：只读上下文，不能调用技能，输出结论。复核不是让模型再猜一次，而是让它指出缺口。

### 三元结论

复核只输出三种结论，不允许模糊表述：

| 结论 | 含义 | 后续 |
|---|---|---|
| 通过 | 现有证据支持执行 | 进入本地执行前检查 |
| 需要证据 | 缺少具体某项数据，必须写明方向、数量、范围和有效期 | 补数据，或转人工补充 |
| 否决 | 已有反向证据或违反硬约束 | 拒绝，并说明违反哪一条 |

「信息不足」「无法判断」这类笼统表述一律按否决处理，所以必须逼出「需要证据」这一档。二元结论会把「没测过」和「测到了危险」压成同一个「不行」，而这正是误拒的主要来源，也让用户无法知道补什么才能继续。

### 需要证据要给具体项

「需要证据」必须写成可核对的条目：哪个方向、要多大净空、持续多久、多少秒内的测量有效。例如「后方净空 ≥ 2 米，测量时间在 5 分钟内」，而不是「确认后方安全」。

### 坐标系由状态估计维护

机器人转身之后，「前方 30 米」就变成了「后方 30 米」。让语言模型自己做这个几何变换必然出错，于是把已经确认过的安全后方又判成未知。方向相关的净空由状态估计按方向维护成表（方向、距离、测量时间与年龄、来源），朝向变化时按航向旋转这个表。模型只读表，不做坐标变换。

### 附带执行条件

复核可以通过并附带确定性条件，例如后方净空 ≥ 2 米、电量 ≥ 20%、半径 2 米内无人。条件在执行时由本地安全层逐项重查，任一不满足就停止并报告实际结果。语义判断留在云端，确定性检查留在本地，中间不靠提示词维持。

### 复核的独立性有限

当前复核与规划是同一进程、同一模型，只是没有工具。它能拦住明显的越权调用和参数错误，但对同一批上下文的误读没有独立视角。结论、缺失的证据项和原始上下文都要落进活动记录，供人事后核对；样本足够后再评估是否换成独立模型或独立提示路径。

## 权限模型与管理员 AI

长期方向是三级权限，按可修改的范围从小到大排列：

| 级别 | 可修改的范围 | 默认状态 |
|---|---|---|
| 一级 | 技能目录（`skills/`），只改技能本身 | 最低权限，常态运行在这一级 |
| 二级 | 运行环境，可运行和修改本程序自身的内容 | 需要授权 |
| 三级 | 完整权限，包含系统内容 | 默认关闭，限时授予 |

授权只能来自一个权限管理员 AI。用户不直接对普通 Agent 说「给你权限」，因为语言理解会被上下文、玩笑和第三方话语带偏。管理员 AI 独立判断：是否确实需要越级、需要哪一级、用多久。授权是有范围的——给二级不等于给三级，给一次不等于给永久。

分级不是为了限制读。读操作默认完全放开，不受级别影响。真正受限的是写和越权执行。

### 无屏机器人的确认

机器人大多没有屏幕，权限确认同样走语音和手势的二元判断：用户只说「确认」或「取消」，或者做 OK 手势、五指张开朝向摄像头做阻拦手势。确认窗口 10 秒，只认紧随提示之后的一次回答，只提示一次，超时即放弃。具体流程见 [15](15-dashboard.md)。

两项必须限制：

- 二级权限要改的是运行时自己的保护和门禁代码，所以二级修改必须走分支或独立工作区，并维护一份受保护文件清单，清单内的文件不允许二级修改。
- 三级权限默认关闭、限时授予，审计记录放在 AI 访问不到的位置。

危险操作和系统修改不靠用户口头确认就放行，走 Dashboard 认证加密码再加限时同意，见 [15](15-dashboard.md)。

### 与「不可自改的项目」的关系

本节描述的是经过授权的越级路径，不改变 [07](07-memory-improvement.md) 中列出的不可自改项目。即使拿到三级权限，急停、避障、碰撞保护、速度硬上限和安全区域边界这些项目仍需要独立的安全验收，不能由 Agent 单独完成。提案和发布流程见 [09](09-extension-lifecycle.md)。

这一节是方向，尚未实现。当前 Agent 没有写入生效配置或修改运行时代的工具。

## 决策上下文

发送给云端模型的上下文由 `third_party/picoclaw` 的 session 与 ContextBuilder 组装，应是与当前任务相关的内容，包括：

- 用户目标和同一 session 内的对话历史；过长时由自有 ContextManager 按完整回合生成摘要；摘要提交校验会话代次与覆盖边界，只移除已摘要的前缀，不静默截断必要历史（见 [18](18-picoclaw-dialogue-context.md)）。
- 当前机器人、可用技能和限制摘要（写入引导文件进入系统提示，不进历史）。每项技能带动作介绍，而不只是技能 ID。
- 最新且未过期的感知状态与数据来源/置信度。
- 当前任务进度、动作结果、失败原因和已尝试步骤（任务结束后以 `note` 写入 session，不再另调模型）。
- 隐私允许范围与需用户确认的操作。
- 获得授权且与当前任务相关的用户偏好/记忆，以及它们的来源和更新时间。

不要在每轮默认发送完整原始传感器流或全部长期记忆。上下文中区分“观察到”“估计为”和“模型推断”，避免将推测呈现成事实。

Agent 可依据反馈分析误唤醒、漏唤醒或交互成功率，并提出 profile 调整建议。MVP 中 Agent 没有写入生效配置的工具；配置变更进入独立提案与验证流程，不能直接变更本地安全规则。

## 重试、超时与幂等

- 模型请求、工具请求和动作命令使用独立的超时与关联 ID。
- 对话生成可按 provider 策略重试；动作不得因模型重试而重复执行。
- 使用 command_id 去重；对不可幂等技能默认不自动重发。
- 模型超时后由事务流决定等待、取消待执行命令或返回可恢复错误。
- 未知/不支持的技能请求应拒绝并给出能力摘要，不允许模型编造后备硬件命令。

## 未来扩展

VLA 或专用策略模型可作为一个技能实现接入，例如 manipulation.pick。其输入/输出仍通过适配器与回环契约，输出需经过本地安全和能力约束。是否使用 VLA 应由具体任务的成功率、延迟、算力、数据与硬件兼容性评估决定，不作为 Agent 基础架构的前提。
