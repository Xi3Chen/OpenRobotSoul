## 贯穿全阶段的约束

这些约束不随阶段推进而放松：

- 高层语义决策在云端，运动控制、安全监督和设备驱动在本地，断连时本地仍能安全停下。
- 所有自然语言最终转写都交给常驻对话进程，不设本地命令快速路径。
- 动作必须通过有参数约束的技能调用，自由文本不直接解释成运动命令。
- `confirm` 级动作必须经过无工具的复核；`high` 级动作普通 Agent 不可调用，只能由已认证的 Dashboard 操作员在重新输入当前账户密码后发起。
- 首版不实现删除/遗忘接口。记忆以文件保存，由 AI 通过文件编辑接口维护，操作员可直接删除对应文件。
- 每一阶段先通过上一阶段的自动化验收，再把动作风险提高一级。任务状态无法从反馈可靠确定时，先修反馈和可观测性，不进入自动重试或扩大动作范围。

## 阶段 0：技术选型与契约冻结（已完成）

交付：

- 首台真实机器人定为 Unitree Go2，模拟器先行；云端模型 provider 通过 OpenAI 兼容接口接入。
- `third_party/picoclaw` 以固定 commit 链接，版本、license 和工具扩展方式已记录；自然语言规划归 `openrobotsoul-dialogue`，Go CLI 编码任务隔离在工作区，两个工具面分开登记。
- 技能清单、事件 schema、任务状态机、能力约束和风险分级已定义。
- 机器人 profile schema、型号身份校验和配置覆盖优先级已定义。
- 运行时语言与部署拓扑锁定：Python 主进程、Go 对话进程、C++ 驱动 bridge、独立 Voice Service。

验收：端到端接口草图通过机器人控制、安全和云端 API 约束检查。具体 SDK 路径和实机能力仍留待阶段 3 冒烟，方案不预设 Topic/API。

## 阶段 1：契约与模拟适配器（已完成）

交付：

- 观测、状态、能力、命令、反馈和评估的数据类型（`robotsoul/models.py`）。
- 模拟适配器，支持模拟传感器事件和技能。
- 多个 profile，能力集合与限制不同，每次运行只加载一个。
- 任务状态机、trace/task/correlation ID 和工具调用审计。

## 阶段 2：单机器人云端 Agent（已完成）

交付：

- `openrobotsoul-dialogue` 接入云端模型，作为文本与语音最终转写的共同规划器，持有 session 上下文。
- 自然语言任务、决策 schema、技能白名单和能力上下文；文本框与语音最终转写同一入口。
- 单一端到端技能执行路径与用户结果答复。

验收：模型无法调用未注册技能；重试不会重复执行物理动作；云端超时可安全结束。

过渡说明：当前实现是 tools=0 加单一 JSON 决策（`act`、`run_rule`、`wait`、`complete`、`clarify`、`reject`、`coding_task`），provider 包装层拒绝非空工具声明。这是首阶段形态，切换原生 tool-calling 的时机定在第一次真实端到端测试之后，理由见 [11](11-agent-tooling-decision.md)。

## 阶段 2A：Agent 底座与语音测试台（底座已交付）

已交付，证据见 [20](20-agent-foundation-implementation.md)：

- 任务回环 `TaskRunner`、SQLite 任务存储、任务内规则调度、独立取消。
- 按身份隔离的不透明会话键与可靠上下文；会话与模型隔离。
- 动作边界（`runtime.py` / `models.py` / `agent.py`）、本地停止、Dashboard 与 API。
- Voice Service 的骨架、设备适配、音源仲裁、KWS/VAD、回复播报和 ASR/TTS API 客户端。
- 两个模拟场景：阳台检查窗户（含未知状态的观测上限）与音频节拍驱动闪灯；256 条命令与 256 条证据在 32768 token 窗口内完成。
- 测试：381 个 Python 用例，375 通过、6 跳过、0 失败；Go 测试通过；三个平台构建成功（linux arm64 只构建未运行，Windows 上没有 Go race detector）。

这个阶段的验收只基于夹具和本地假 provider，所以还不能说「端到端跑通」。剩余工作如下，全部完成才算阶段 2A 关闭：

| 事项 | 现状 | 完成判据 |
|---|---|---|
| 首次真实端到端测试 | 只有夹具与假 provider | 真实模型 + 对话进程 + 模拟器，语音进、语音出，完成一次技能选择、执行、反馈和答复 |
| 分段计时 | 无真实数据 | 唤醒、ASR final、决策、首个 reply、TTS 首包各自有 p50/p95 记录，并记录真实模型的 JSON 稳定性 |
| `retry_safe` 登记 | 代码解析该字段，但四个 profile 都没登记，`retry_limited` 的重试实际全被拒绝 | 逐技能评估幂等性后登记；评估为不安全的保持拒绝 |
| 稳定 request id | Go 宿主未生成 | 每次请求带宿主生成的稳定 id，运行日志与工具调用审计可关联 |
| 流式 ASR | 只有整句 `POST /audio/transcriptions`，无 partial | 支持流式端点，partial 只用于显示、日志和计时，不用于提前执行 |
| 任务/动作历史与 WAL 保留 | 无策略 | 定保留期、清理时机与磁盘上限 |
| 共享任务库单写者 | 无保护 | 明确唯一写者，或加锁 |
| 稠密时间线持久化 | 长任务下呈 O(n²) | 事件量翻倍时持久化耗时线性增长 |
| Dashboard 全量测试偶发失败 | 未定位 | 连续多轮全量通过 |

交付顺序：先做首次真实端到端测试，它决定 tool-calling 切换、speculative 评估和语音延迟预算的后续取舍；`retry_safe` 与 request id 紧随其后，因为重试和审计都依赖它们。流式 ASR 可以与 2B 并行，不阻塞。

验收：真实 provider 下文字与语音两个入口都能完成一次技能选择、执行、反馈和答复；对话进程重启后上下文可恢复；分段延迟有记录。真实 Go2 与手机的同步精度、导航和视觉不在本阶段验收。

## 阶段 2B：动作复核与确认通道（开发完成）

排序原因：阶段 3 起的动作会产生位移和不可逆后果，而机器人大多没有屏幕。没有确认通道，`confirm` 级动作只能靠人工在旁边盯着，实机验收无法进行。这一阶段必须早于阶段 3。

交付：

- 复核三态改造。当前 `SafetyReviewer` 只有 allow / deny / uncertain（`runtime.py`、`gateway.go`），改为「通过 / 需要证据 / 否决」。`需要证据` 必须写明方向、数量、范围和有效期，例如「确认身后 1 米内无人」；含糊的「信息不足」按否决处理。
- 复核结论与执行条件分开。复核可以给出「通过，附带条件」，条件由本地安全层在执行时确定性重检；条件不满足则拒绝执行，不回头再问模型。
- 语音二元确认。KWS 闭集只含「确认 / 取消」；播报期间 KWS 静音并加约 200 ms 守候；独立 10 秒计时，不复用 `follow_up_seconds`；只接受第一句；只允许本地麦克风；方向门控；多人同时说话按「没听清」处理；不可逆动作要求唤醒词前缀（例如「索拉，确认」）；提示只播一次，超时或未听清一律放弃（fail-closed）；确认窗口开启时有可感知的提示音或灯。
- 手势确认。OK 手势表示同意，掌心上推表示全局停止（不限于确认窗口）；要求保持 ≥0.5 秒、面向相机、距离有效。不可逆动作要语音和手势同时具备，因为单手势识别可能被一张照片骗过。
- Dashboard 确认。关闭安全保护、修改避障开关和系统配置走已认证操作员加重新输入当前账户密码，授权绑定到具体动作，并受时间和次数限制。
- 状态估计维护用于复核的证据。按方向维护净空表（方向、距离、测量时间、来源），机器人转向时随之旋转；模型不做几何换算。没有证据可以由人证补上，反向证据不能被口头否认覆盖，只能走 Dashboard 认证加密码。
- 误拒的度量。记录复核否决、需要证据和执行条件不满足的次数与原因，在 Dashboard 可见；误拒率是后续调参依据。

验收：可逆 `confirm` 动作能被一次单字或一次手势确认并执行，10 秒内无响应则放弃；不可逆动作在缺唤醒词前缀或缺手势时被拒绝；反向证据存在时口头确认无效；执行条件在动作发起和落地前各重检一次；确认通道的全部失败路径都不会导致误执行。

实现落点：`robotsoul/models.py` 定义复核三态、证据要求和执行条件；`robotsoul/confirmation.py` 实现本地麦克风二元确认、手势确认、10 秒一次性窗口和全局停止；`robotsoul/safety.py` 维护带有效期的方向证据、反向证据优先级和本地条件门禁；Runtime 在适配器调用前后重检，Dashboard 暴露复核/拒绝指标并对避障和自动恢复开关执行密码 step-up。

## 阶段 3：真实动作反馈与评估（开发完成，实机冒烟待目标设备）

交付：

- Go2 真实适配器接入，完成连接、身份校验、能力探测和首个实机冒烟。
- accepted / running / succeeded / failed / cancelled 反馈映射。
- 传感器、里程计和控制器状态参与任务评估。
- 本地安全监督：急停、速度上限、区域约束、控制器 watchdog 和断连策略。

验收：实际执行结果与任务评估一致；本地急停、低速限制和云端断连策略在实机通过验证；`confirm` 与 `high` 级动作的前置条件在真实硬件上按阶段 2B 的规则生效。阶段 0 遗留的 SDK 路径、通信方式和传感器能力在进入本阶段前确认，无法确认的能力不写入 profile。

实现落点：Go2 bridge 已完成身份/API 版本握手、能力探测、SportClient 反馈生命周期、Sport/LowState/IMU/里程计观测和断连 fail-closed；`LocalSafetySupervisor` 对连接 watchdog、急停、速度上限、授权区域和落地状态提供确定性门禁。当前环境没有连接 Go2，故实机动作、急停响应时间和硬件通信稳定性仍需在目标设备执行冒烟。

## 阶段 4：语音交互完整验收（部分实现）

已实现：Voice Service 本体、设备适配、音源独占与状态机、中文 KWS、VAD、整句 ASR、TTS API 播放、Dashboard WebRTC 通话、回复优先播报。

未完成：

- 流式 ASR 的 partial 通道（与阶段 2A 的流式项合并推进）。
- ASR/TTS 本地服务自动拉起：`base_url` 为空的一端由宿主启动本机后台服务，环境变量覆盖视为已配置，地址运行时注入不写回配置，由 Health Supervisor 监督。目前两侧都未实现。
- 打断（barge-in）与 AEC 在目标板上的可行性。
- 目标板时延预算实测、噪声与多语者场景、10 小时长跑。

验收：通过音源并发与切换契约测试、无设备休眠测试、媒体断线恢复测试、目标板时延测试和至少 10 小时混合负载测试；唤醒短语或挥手后说话能形成 Agent 任务；只有挥手、低置信或过期事件、无语音、多人歧义和超时不会误发动作；说话对象不明确时回到 PASSIVE 或要求再次唤醒；摄像头/麦克风提示、授权和数据保留策略已验证。基于 partial 的提前执行在本阶段拿到数据后再决定是否启用。

## MVP 范围说明

阶段 0 至 4（含 2A、2B）构成 MVP 验收范围。阶段 5 至 9 是 MVP 之后的设计储备：设计保留，不进入 MVP 验收，不占用 2A 至 4 的工期。

三级权限模型（技能目录 / 运行环境 / 系统）不在 MVP 内实现。MVP 只需要保证 Agent 没有写入生效配置或修改运行时代的工具；越级授权入口留到权限管理员 AI 设计落地时再开，见 [03](03-agent.md)。

## 阶段 5：记忆与受控自我改进（MVP 后）

交付：

- 用户偏好、短期任务上下文和历史任务结果分层存储。
- 单实例下 robot_id/device_id 的数据隔离与显式读取策略。记忆以文件保存，由 AI 通过文件编辑接口维护，操作员可直接删除对应文件，不另设删除接口。
- 误唤醒/漏唤醒指标、带证据的策略变更提案、回放/影子测试、维护者批准、版本部署与回滚。
- 增加第二种传感器适配器，或在隔离测试部署中增加第二个机器人型号 profile。

验收：Agent 不能直接写运行配置；未经授权的变更不生效；获批的 profile 版本可以回滚。记忆错误、过期和遗忘行为均可测试——遗忘由 AI 改写记忆文件完成，不经过独立的删除接口。

## 阶段 6：受限主动行为（MVP 后）

交付：

- 本地主动任务资格策略，基于电量、健康、任务队列、环境风险、用户偏好/静音时段和允许区域判断。
- 先实现低频、可取消的问候；再在已知且授权的区域实现限速、限时、限距离探索。
- 用户呼叫、障碍或人员风险、低电量、传感器故障、急停或云端失联时的中止流程。

验收：任一资格不满足时不创建主动任务；执行中条件失效时本地停止或暂停；Agent 不可扩大区域和动作边界；主动问候遵守频率上限和免打扰设置。

## 阶段 7：环境记忆与能量管理（MVP 后）

交付：

- 经定位/建图能力验证的地图候选更新、版本比较和禁区保护。
- 经用户授权的熟人目录、最近交互和招呼偏好；记录以文件保存，删除由操作员直接处理。
- 低电量、返航余量、充电点可达性、求助和 savepower 状态机。

验收：地图候选不能扩大授权区域；未经确认的人不进入熟人目录；低电量决策按设备反馈完成返航、充电、求助或 savepower，不能只按工具返回推断成功。

## 阶段 8：启动监督与自恢复（MVP 后）

交付：

- 独立 Supervisor、last-known-good 发布槽、启动健康检查和恢复模式。
- 本地自动回滚、重复崩溃隔离、恢复日志和断网安全待机。
- 云端诊断提案的隔离工作区、测试门禁和授权发布流程。

验收：损坏版本启动失败时断网也能安全回退；当前版与 last-known-good 都失败时进入恢复模式而非无限重启；修复流程不会覆盖记忆、地图或凭证。

## 阶段 9：插件扩展与受控代码改进（MVP 后）

交付：

- 插件声明、风险分类、权限沙箱、签名包和确定性发布门禁。
- PicoClaw 在隔离工作区生成插件或补丁；低风险预授权插件通过门禁后可自动 canary 部署，其他变更走批准流程。先完成编码能力、权限隔离和工具协议评估，再启用部署链路。

验收：仅在阶段 8 恢复机制通过后启用自动发布；L0/L1 预授权插件通过自动门禁后可部署并可回滚；新增动作权限、唤醒策略及核心代码未经批准不部署。这里的 L0–L3 是变更风险，与 03 的三级权限不是同一套编号，见 [09](09-extension-lifecycle.md)。

## 推进顺序与退出条件

近期顺序：

1. 阶段 2A 的首次真实端到端测试。它同时回答三件事：真实模型的决策稳定性、语音链路的真实延迟、tool-calling 是否该切换。
2. `retry_safe` 登记与稳定 request id。
3. 阶段 2B 的复核三态与确认通道。
4. 阶段 3 的实机接入，前提是 2B 的失败路径已经验证。

任一阶段若任务状态无法从反馈可靠确定，先修反馈或可观测性，不进入自动重试或扩大动作范围。每阶段先完成上一阶段的自动化验收，再把动作风险提高一级。
